운영 중인 플랫폼에서 여러 조회 화면이 느리다는 제보를 받았다. 처음엔 단순히 "인덱스를 더 걸면 되겠지"라고 생각했고, 실제로도 일부는 그 방식으로 해결됐다.

하지만 자세히 보니 화면마다 병목이 전혀 달랐다. 결국 각 화면에서 실제로 무슨 조건이 느리게 돌아가고 있었는지 확인한 뒤, 처방을 각각 다르게 적용해야 했다.

## 시작은 공통: `ANALYZE FORMAT=JSON`

진단에는 공통으로 `ANALYZE FORMAT=JSON`을 사용했다. `EXPLAIN`은 옵티마이저의 추정이고, `ANALYZE`는 실제로 쿼리를 실행한 뒤의 실측 결과를 보여준다.

```sql
ANALYZE FORMAT=JSON
SELECT ...
```

이 결과에서 가장 중요하게 봤던 건 다음 세 가지였다.

- `r_rows`: 실제로 읽은 행 수
- `r_loops`: 반복 실행 횟수
- `r_total_time_ms`: 해당 연산이 실제로 소요한 시간

추정치와 실제 값의 차이가 큰 지점이 곧 잘못 판단된 실행 계획이었고, 시간이 많이 잡히는 지점이 실제 병목이었다...

## 처방은 화면마다 달랐다

결론부터 말하면, 네 화면의 느린 이유는 전부 달랐다.

- 단말기 화면: 인덱스 부족
- 계량기 화면: 쿼리 로직 자체의 비효율
- 탱크 화면: 조회 시점의 계산 중복
- 용기 화면: 조회 시점의 계산 중복

같은 "느림"이라도 원인이 다르면 처방도 달라야 한다.

### 1) 단말기 화면 — 인덱스 추가로 해결

가장 단순한 케이스였다. 쿼리 구조 자체는 크게 문제 없었고, 자주 쓰는 조건에 맞는 인덱스가 없어서 테이블 전체를 훑고 있었다.

해당 조건에 맞는 인덱스를 추가해주자 바로 개선됐다.

```sql
ALTER TABLE device_table
  ADD INDEX idx_condition (condition_col),
  ALGORITHM=INPLACE, LOCK=NONE;
```

운영 중인 테이블이어서 `ALGORITHM=INPLACE, LOCK=NONE`를 넣어 무중단에 가까운 방식으로 인덱스를 추가했다.

> 인덱스 하나로 해결될 수 있는 문제와, 그렇지 않은 문제를 구분하는 것이 성능 튜닝의 첫 시작이다..!

### 2) 계량기 화면 — 쿼리 재작성

계량기 화면은 인덱스만으로는 해결되지 않았다. 원인은 쿼리 로직 자체였다.

기존 방식은 특정 구간의 값을 전부 합산해, 결과가 0인지 확인하는 방식이었는데, 이 방식은 조건에 맞는 데이터를 찾기 위해 수많은 행을 읽어야 했다.

그래서 로직을 바꿨다. 전체 합계를 다시 계산하는 대신, 현재 값과 이전 시점의 최근 값을 비교하는 방식으로 바꾼 것이다.

```sql
-- 개선 전: 구간 전체를 읽고 합산
-- 개선 후: 최근 값 비교로 불필요한 스캔 제거
```

핵심은 읽어야 하는 행 수를 줄이는 것이었다. 같은 결과를 얻으려면 전체를 훑는 것보다 최근 한 건만 비교하는 편이 훨씬 효율적이었다.

추가로, 불필요하게 넓은 범위를 읽지 않도록 조건을 더 좁히는 부분도 함께 정리했다.

### 3) 탱크 / 용기 화면 — 요약 테이블 도입

이 두 화면은 더 근본적인 문제였다.

조회할 때마다 원본 이력 테이블에서 최신 상태를 다시 계산하고 있던 구조였다. 탱크 화면은 최종 충전 이력을, 용기 화면은 최종 절체일을 매 조회 시점마다 다시 찾고 있었고, 수천만 건의 이력 테이블을 조회하면서 큰 비용이 발생하고 있었다.

문제는 "최근 상태"가 그때그때마다 새로 계산해야 하는 값이 아니라는 점이었다. 데이터가 들어올 때만 갱신되면 충분한 값인데, 조회 시점마다 다시 계산하는 건 비효율적이었다.

그래서 요약 테이블을 만들었다.

- 탱크 화면: 최종 충전 이력 요약 테이블
- 용기 화면: 최종 절체일 요약 테이블

원본 이력 테이블에는 `AFTER INSERT` 트리거를 걸어, 새 데이터가 들어오는 순간 요약 테이블을 갱신하도록 했다. 조회 시점에는 원본 테이블을 훑는 대신 이미 계산된 요약 테이블만 읽게 만들었다.

```sql
-- 원본 이력 테이블에 insert 후 요약 테이블 갱신
-- 실시간으로 누적하고, 조회는 요약 테이블 기반으로 처리
```

이 방식의 핵심은 계산 시점을 "조회할 때"에서 "데이터가 들어올 때"로 옮긴다는 점이다.

조회가 자주 일어나는 화면에서는 이 방식이 훨씬 안전하고 효율적이다. 다만 요약 테이블은 운영 복잡도가 올라가므로, 꼭 필요한 곳에만 적용하는 게 중요하다.

## 튜닝의 기준

이렇게 네 화면을 정리해보니 기준이 조금 명확해졌다.

- 인덱스 부족: 인덱스 추가
- 쿼리 로직 문제: 로직 재작성
- 조회 시점 계산 중복: 요약 테이블

같은 "느리다"라고 해도 원인은 전부 다르다. 무조건 인덱스부터 건드리면 오히려 비효율적인 경우가 생기고, 요약 테이블처럼 무거운 처방도 지나치게 많이 쓰면 운영 부담이 커진다.

그래서 최적화는 "문제에 맞는 최소한의 처방"을 고르는 작업이라고 생각한다.

## 결과

이후 조회 화면들은 모두 개선됐고, 가장 먼저 느리다는 제보가 들어왔던 화면도 거의 대부분 정상화되었다.

하나만 보면 "성능 튜닝 = 인덱스 추가"로 단순화되기 쉬운데, 실제 운영에서는 그렇지 않다. 어떤 안에서 병목이 생기는지 정확히 확인하는 것이 가장 중요했고, 그 과정에서 실행계획을 실측하는 습관이 가장 큰 도움이 되었다.
