처음 문제를 찾을 때는 쿼리 자체가 느린 줄만 알았고, 병목이 어디인지도 대략 짐작하고 있었다. 가장 먼저 한 일은 불필요하게 한 번 더 감싼 부분을 없애는 것이었다.

결과적으로는 효과가 있었다. 전체를 한 번 더 감싸 조회할 때보다 속도가 절반이나 줄었다.

그래도 완전히 해결되지는 않았다. 그다음에 느린 화면을 다시 확인해보니, 특정 시간대에만 오래 걸리는 패턴이 보였다. 평소에는 조금 느리지만 괜찮고, 아침 첫 로드처럼 캐시가 비어 있는 순간에만 심하게 느려지는 양상이었다.

## 확인한 것: 콜드캐시, 아니면 버퍼 풀에서 읽고 있나?

이럴 때는 단순히 `EXPLAIN`만으로는 부족했다. 실제로 버퍼 풀에서 데이터를 로딩하는 비용인지, 아니면 쿼리 자체의 구조 문제인지 구분해야 했다.

그래서 아래처럼 확인했다.

```sql
-- ① 느린 쿼리 실행 직전
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_reads';

-- ② 여기서 즉시 느린 쿼리를 1회 실행
SELECT ...

-- ③ 실행 직후
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_reads';

-- 캐시가 아닐 경우 대비
SHOW STATUS LIKE 'Created_tmp_disk_tables';
```

그리고 실제 값은 다음과 같았다.

```text
281233071
281239611
8
```

핵심은 첫 숫자와 두 번째 숫자 차이다.

- `281233071` → 느린 쿼리 실행 직전 값
- `281239611` → 느린 쿼리 실행 직후 값

차이는 `643?` 정도로 보이지만, 핵심은 **버퍼 풀 리드 수가 분명히 증가했다는 점**이다.

즉, 그 쿼리를 한 번 수행하면서 **버퍼 풀에서 페이지를 읽어오지 않았던 상태에서 캐시 미스가 발생했다**는 뜻이다. 평소엔 버퍼 풀에 남아 있는 데이터라 빠르게 보이지만, 첫 로드 시에는 디스크에서 페이지를 읽으면서 느려진 거였다.

여기서 `Created_tmp_disk_tables` 값은 `8`로, 임시 테이블이 디스크에 생성된 수치가 아니었다. 이건 지금 케이스에서 최적화 포인트가 **캐시 상태**였음을 뒷받침하는 근거였고, 전반적인 쿼리 구조 자체보다 먼저 보아야 할 게 콜드캐시였다는 결론으로 자연스럽게 이어졌다.

## 실제 원인: 첫 로드에서만 캐시가 비어 있었던 구조

문제 쿼리는 대략 다음 구조였다.

```sql
SELECT x1.*
FROM (
    SELECT
        d.key_id,
        d.key_type,
        DATE_FORMAT(d.inpt_dttm, '%Y-%m-%d %T') AS inpt_dttm,
        s.sort
    FROM data_daily d
    JOIN menu_list s
      ON s.key_id = d.key_id
     AND s.key_type = d.key_type
    WHERE d.key_id = 'abcde'
      AND d.inpt_dttm >= DATE_SUB(DATE_FORMAT(NOW(), '%Y-%m-%d 00:00:00'), INTERVAL 6 MONTH)
      AND d.key_type NOT IN ('7', '8', '9')
    GROUP BY d.key_type, DATE_FORMAT(d.inpt_dttm, '%Y%m%d')
) x1
WHERE 1 = 1
GROUP BY x1.key_type, x1.inpt_dttm
ORDER BY x1.inpt_dttm DESC, x1.sort;
```

이 쿼리의 핵심은 **같은 데이터가 반복해서 조회될 때마다 버퍼 풀 상태가 달라진다는 점**이었다. 쿼리 자체를 바꾸는 것도 중요했지만, 이 케이스에서는 첫 로드에서 캐시가 비어 있는 순간에 페이지를 읽는 비용이 더 큰 병목이었다.

아침처럼 캐시가 비어 있는 순간에는 여전히 느린 상태가 남아 있었고, 그건 단순히 조건문만으로 해결할 수 있는 문제가 아니었다.

## 왜 콜드캐시에서 느렸는가

우리가 확인한 값으로 볼 때, 쿼리 직후 버퍼 풀 리드 수가 증가했다는 건 다음을 의미한다.

- 이 쿼리의 데이터가 버퍼 풀에 안 들어가 있음
- 첫 조회 시점에 InnoDB 페이지를 로딩해야 함
- 그 로딩 비용이 응답 시간에 직접 반영됨

즉, 쿼리의 논리적 복잡도보다도, **초기 부하 시 버퍼 풀 상태**가 더 큰 영향을 주고 있던 셈이다.

운영 환경에서는 이런 경우가 종종 있다. 평가 대상이 "절대적인 쿼리 성능"이 아니라, 첫 로드, 새 서버, 새 컨테이너, 캐시 비움 상태에서의 로딩 시간일 수 있다.

## 결론

이번 케이스에서 가장 중요한 건 단순히 조건을 줄이는 일보다, **캐시 상태를 고려한 병목을 분리해서 보는 습관**이 필요하다는 점이었다.

- 불필요하게 한 번 더 감싸 조회하는 부분 제거
- 콜드캐시 확인: 첫 로드에서 느린 원인 구분
- `Innodb_buffer_pool_reads` 확인: 캐시 미스 여부 실측

결국 이건 "쿼리 로직 문제를 해결했다"보다는, **쿼리 구조와 캐시 상태가 함께 작용하는 병목 문제**로 정리하는 게 맞다.

이 문제는 지금도 완전히 마무리되지는 않았다. 쿼리를 더 정리하고, 자주 쓰는 데이터의 캐시 히트율을 높이는 방향으로 더 보완할 여지가 남아있다.


> 조건을 줄여서 일부 병목을 제거했지만, 첫 로드 시 콜드캐시가 남아 있는 상황에서는 여전히 느린 지점이 있다. 그래서 쿼리 구조 개선과 캐시 전략 개선을 함께 보완해야 한다.
