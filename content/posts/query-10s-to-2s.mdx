매달 반복되던 클레임이 있었다. "이번 달 검침 조회가 왜 이렇게 느려요?" 처음엔 서버 리소스 문제인 줄 알았는데, 슬로우 쿼리 로그를 열어보니 범인은 따로 있었다.

## 증상: 조회할 때마다 10초

이번 달 사용량을 보여주는 화면이었다. 쿼리 자체는 평범해 보였다.

```sql
SELECT device_id, usage_value, measured_at
FROM meter_readings
WHERE DATE_FORMAT(measured_at, '%Y-%m') = '2026-07'
  AND site_id = 128
ORDER BY measured_at;
```

`measured_at`에는 인덱스가 있었다. 그런데도 느렸다. `EXPLAIN`을 찍어보고서야 이유를 알았다.

```
type: ALL
rows: 48213902
Extra: Using where; Using filesort
```

`DATE_FORMAT(measured_at, '%Y-%m')`처럼 컬럼을 함수로 감싸는 순간, 옵티마이저는 인덱스를 탈 방법이 없다. 5천만 행을 전부 스캔한 다음에야 조건에 맞는 행을 걸러내고 있었던 것이다.

## 처방: 범위 조건으로 바꾸기

함수로 가공하지 않고, 인덱스가 그대로 이해할 수 있는 **범위 조건**으로 바꿨다.

```sql
SELECT device_id, usage_value, measured_at
FROM meter_readings
WHERE measured_at >= '2026-07-01 00:00:00'
  AND measured_at <  '2026-08-01 00:00:00'
  AND site_id = 128
ORDER BY measured_at;
```

그리고 `(site_id, measured_at)` 복합 인덱스를 새로 걸었다. 운영 중인 테이블이라 락 없이 넣어야 했다.

```sql
ALTER TABLE meter_readings
  ADD INDEX idx_site_measured (site_id, measured_at),
  ALGORITHM=INPLACE, LOCK=NONE;
```

> `ALGORITHM=INPLACE`와 `LOCK=NONE`을 명시하지 않으면 MariaDB가 기본 알고리즘을 골라버릴 수 있다. 대용량 테이블에서는 이 두 옵션을 꼭 확인하는 습관이 생겼다.

## 결과

```
type: range
rows: 41230
Extra: Using index condition
```

체감상으로도 확실했다. **10초 → 2초**, 약 80% 단축. 스캔하는 행 수가 4천8백만에서 4만 수준으로 줄었으니 당연한 결과였지만, 숫자로 확인하고 나니 실행계획을 실측하지 않고 감으로 튜닝했다면 절대 못 찾았을 병목이라는 생각이 들었다.

## 오늘의 배움

- 컬럼을 함수로 감싸는 조건(`DATE_FORMAT`, `YEAR()` 등)은 인덱스를 못 탄다. 항상 범위 조건으로 바꿀 수 있는지 먼저 확인하자.
- "느리다"는 감으로 판단하지 말고 `EXPLAIN`으로 먼저 실측하자.
- 운영 중인 대용량 테이블에 인덱스를 추가할 땐 `ALGORITHM=INPLACE, LOCK=NONE`을 챙기자.
